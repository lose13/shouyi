# Gemini 与守忆守则：官方28轮对照

## 运行前固定的方案

- 用户选定 `gemini交付包/memory-rules.md` 原文（V1.4），而非 `track3_submission` 中同名、同版本号但内容不同的较短文件。
- 对照组为当前守忆 v2.4 原文。两份原文均冻结，不按本次结果增删守则。
- 两组都使用冻结的守忆 v2.4 `model.py`、`engine.py`，DeepSeek 官方 API 的 `deepseek-flash`，关闭思考模式，temperature=0；每轮通常一次调用，结构、证据或属性校验失败最多一次模型修正，网络失败不自动重试。
- 分别从空记忆开始。相同的28轮官方输入、可信来源、传输脱敏、最近8轮上下文策略、状态存储和Markdown导出方式。两组按轮次交替运行，记忆相互隔离。模型不接收主人背景卡、预期答案、另一组结果或后续输入。
- 旧版 v2.2.1 已有完整28轮结果单独保存为历史参考；它不与当前代码的重跑混称同条件实验。

## 接口适配与边界

原应用的提示中包含守忆专用条款编号，也有重复语义要求。直接接入另一份守则会引用错章节。本实验在冻结代码运行时为两组共同替换 `PROTOCOL`，内容完整保存于 `common-protocol.txt`，主要定义相同的JSON字段和校验约束。应用源文件和两份原版守则均不修改。必须把这个适配作为实验条件报告。

Gemini 的 `PENDING_VERIFY` 以应用的 `UNVERIFIED` 表示，`[待确认]` 以 `REVIEW` 表示；固定安排 `SCHEDULE` 用 `PREFERENCE` 表示。原应用的 `validity` 和 `observations` 仍是两组共同必填的接口字段，因此这不是让两组自由生成Markdown，也不是运行Gemini原应用。格式负担与上下文组织仍可能影响结果。

本系统依据可信来源限制第三方写入，也不具备Gemini守则描述的 `PENDING_NOTIFY` 临时事务队列与后台主动提醒；官方28轮中的第三方是隐私索取或篡改场景，本次不能证明该队列机制的好坏。系统同样没有“密文托管”服务，模型如果声称存在，需计为实现表述不实。

## 比较口径

逐项核对真实最终状态：身份、工作、居住与通勤、家庭教育、健康与关联取药安排、证书与备考、固定活动、定性待遇变化、已撤销机会、凭据脱敏、传闻和不应记的内容。检查回复是否声称保存了实际未写入的内容。分别报告差异、错误和合理取舍，不用条目总数代替质量，不把项目判断称为官方标准答案。

这次每份守则只完整跑一次。两份文本的长度、内容与结构同时不同，因此结果不能单独证明文本长度的因果影响，也不能据此给出模型稳定性或泛化准确率。字符数仅用于直观比较，真正输入量使用供应商返回的prompt_tokens；历史记忆长度会随各组决策变化。

## 数据留存

每轮保存实际请求标识、时间、用量、版本摘要、失败和修正次数。最终记忆仅从28轮实际执行后的状态导出。删除操作沿用原应用的工作区清理逻辑，不复制已删除草案到独立明细。官方原始输入单独保存是测试材料，不能将其误认为运行中的角色记忆。密钥仅从隐藏输入读取，不写入这些文件。原有提交目录中的记忆和正式结果不被本实验替换。
