# Gemini 原版守则实跑28轮：与守忆记忆的差异

日期：2026年10月16日。模型：DeepSeek 官方 API `deepseek-flash`，非思考模式。

## 先说明实际完成了什么

用户指定的 `gemini交付包/memory-rules.md` 原版 V1.4 已在守忆后台完成全部28轮，最终文件为 `gemini_delivery_v14-memory-LIMING.md`。第11轮首次决策和一次格式修正均未通过，保留失败后从该轮人工续跑成功；总计30次真实API调用，不是28次无失败直通。

同时尝试用相同冻结后台、相同共同接口运行当前守忆 v2.4。该组第6轮失败后续跑成功，第7轮连续两次运行尝试均在一次模型格式修正后仍失败，最终只有6轮保存成功，共12次API调用。没有为它编造第7至28轮或导出“最终记忆”。这些失败也未被删去。

因此，下文完整角色记忆的主比较是：**本次 Gemini 的28轮结果，与用户此前已经得到的守忆 v2.2.1 完整28轮结果**。当前 v2.4 的6轮只用于描述实际观察到的问题，不能把它与完整28轮的总条目数比较，也不能宣称完成了两份守则的同条件全程对照。

本次新增42次调用均有请求标识，共473,657 tokens。历史结果的28次调用和260,615 tokens不是本次新增费用。费用未按未经核实的单价折算。Gemini与历史守忆之间的用量差还包含接口、历史内容、版本和失败重试的影响，不能直接作为守则长度的成本因果估计。

## 当前新版暴露出的接口问题

当前v2.4在第6轮首次因“候选信息取舍与操作映射不一致”失败，保留现场后续跑成功；第7轮两次尝试都因“候选信息与实际操作未逐项对应”失败。每次失败前已经执行一次模型修正，没有程序补写候选或实际事实。

Gemini组第11轮也遇到同类映射校验失败。这说明这些字段和对应要求也会造成运行负担。这个观察支持先检查接口复杂度，不能用它证明“只要把记忆守则写得更长就会更准”，也不能证明某个模型内部的注意力机制就是唯一原因。

这里的未通过不表示对应事实必然理解错了；它表示系统没获得可执行、通过校验的完整决策。运行可靠性本身仍是比赛应用质量的一部分。当前新版尚不具备“在本次共同接口下稳定完成28轮”的证据。

## 本次能得出的判断

1. 用户指定的Gemini原版确实可以驱动守忆后台完成28轮；主要事实更新、明确遗忘、传闻与越权场景都能工作。
2. 以完整记忆的内容来看，此前守忆在关联事项待确认、PMP结果表达、证据确定程度和实际隐私能力表述上更合理；两份结果仍共同存在定性事实遗漏、闲聊混入、回复比证据更强的问题。
3. 不能因为守忆在上述内容上有优点，就宣称当前新版整体更稳定。它在额外同条件运行中实际卡住，新增字段与映射约束需要认真审视。
4. 本次不支持“Gemini因为文本更短所以更好”这个结论：选定文本实际更长，且两份文本的内容、组织也不同。要研究纯长度影响，应另做语义等价的精简实验，保留相同接口并重复运行；本次没有执行该实验。
5. 可以借鉴Gemini按章节说明任务的表达方式，但不能直接照搬“密文托管”等当前系统没有实现的能力。当前更应先减少重复、审视接口负担，再用真实结果判断，而不是逐错追加条文。

## 文件与可复核性

- `gemini_delivery_v14-memory-LIMING.md`：本次实际完成的Gemini守则最终记忆。
- `historical-v2.2.1-memory.md`：用户此前完整守忆记忆的原样副本。
- `gemini_delivery_v14.json`、`historical-v2.2.1-run.json`：对应逐轮状态、操作、模型请求与用量。
- `shouyi_v24.json`：本次新版6轮成功状态及全部3次失败尝试，无伪造最终文件。
- `metrics.json`：从记录机械统计的数字，不含语义正确率评分。
- `rules/`：冻结的原始守则；`frozen-source/`：冻结的应用源代码。
- `common-protocol.txt`、`实验说明.md`：共同接口的全文与适配限制。模型调用时只覆盖运行中的PROTOCOL常量，未替换原应用文件。

两份28轮完整结果的程序和协议版本并不相同；当前同条件全程比较没有完成。这份报告提供实际差异与失败证据，不给出总体准确率排名、泛化结论或官方评分。两份结果只各完成一次，未运行留出集，未更改正式提交目录里的守则、记忆、运行结果或平台日志。
